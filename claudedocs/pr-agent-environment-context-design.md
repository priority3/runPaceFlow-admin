# PR Agent「环境感知」改造方案(仅设计,不含实现)

> 2026-07-20 · 针对问题:回答死板,全部围绕睡眠/恢复/身体数据,忽略天气、时段、地点等基础外部事实
> 证据样例:`claudedocs/pr-agent-eval-2026-07-16T09-21-26-735Z/failures/l2-run-today.md`

## 一、问题现象

问「今天适合跑步吗?」,PR 的完整决策链是:HRV 48 → 睡眠 405 分钟 → 恢复 okay → 8 天没跑 → 半马还有 24 天 → 结论"可以跑,控制强度"。全程一次都没考虑:

- **今天天气**:会不会下雨?38°C 高温还是适跑的 15°C?风大不大?
- **现在几点**:context 只有日期没有时刻,PR 连"现在是晚上还是清晨"都不知道,却在回复里说"晚上跑的话记得热身"(纯猜)
- **空气质量**:AQI 爆表天照样会说"可以跑"
- **地点/周边**:常跑路线有没有封路、赛事、施工(如西湖景区节假日人流)

这不是某一轮的偶发,而是**结构性必然**——agent 的世界里根本不存在这些信息。

## 二、根因分析(4 个,都在代码里)

### 1. 上下文装配只有「关于用户自己」的数据

`src/lib/pr/chat.ts` build_context 装配的 8 路数据:记忆、知识库、历史消息、健康快照、比赛目标、伙伴画像、最近活动、各类型最近一次——**全部是内部库的自我数据,外部世界 0 注入**。`buildChatContextTurn`(`src/lib/pr/prompts.ts`)的 6 个 context 区块同构。

### 2. 工具集封闭

`src/lib/pr/tools.ts` 只有 `query_activities` 和 `query_health_daily` 两个内部只读查询。agent 即使"想到"天气,也无工具可查。

### 3. System prompt 主动收窄(关键放大器)

pr-chat-v7 两条规则:

> 「只依据给你的『事实 / 长期记忆 / 训练知识 / 身体数据』说话;没依据就说不确定,别编」
> 「训练/身体的问题:把恢复、最近负荷、目标日期放前面」

反幻觉红线本身是对的(L4 评测全守住靠的就是它),但副作用:**模型被显式禁止谈论任何上下文外的事实**。它连"今天要是下雨就路滑"这种常识都不敢说——说了就违反"只依据给你的"。回答死板恰恰是 prompt 遵循度高的表现,不是模型能力问题。第二条则把"身体维度优先"写死成了唯一视角。

### 4. 评测同构强化

45 条评测用例与裁判 rubric 全部围绕内部数据正确性(fabricated_fact 对照工具返回),没有任何用例考察"该看天气没看"。优化循环被锁死在内部数据维度上,越评越死板。

### 有意思的对照

代码库其实已有天气能力:`src/lib/weather/open-meteo.ts` 在活动同步时用 Open-Meteo **Archive API** 回填历史天气,跑后复盘 prompt 也引用 `weatherDescription`。说明"天气影响跑步"在产品认知里早已存在——只是 chat 链路缺**前向(预报)**能力。

## 三、设计目标与原则

1. **红线不动**:外部事实同样"查到才说",不能为了不死板放开幻觉口子。因此必须**先给数据/工具,再放开 prompt**,顺序不能反。
2. **复用既有哲学**:FactLoader 快照 + "快照不够就用工具查",新维度照同样模式接入;每路数据独立降级(`.catch(() => null)`),外部 API 挂了不影响对话。
3. **单用户、延迟敏感**(p50 5.9s):快照走缓存,重查询走工具按需触发。
4. **防新死板**:目标是"哪个维度有显著信号就说哪个",不是"每次都播报天气"。

## 四、方案分层

### P0 —— 环境快照 + 时刻感知 + prompt 三轴改造(免费 API、无新依赖)

**4.1 新增 Environment FactLoader**(建议 `src/lib/pr/environment.ts`)

注入一个新的 context 区块 `# 现在的环境(实况与预报)`,内容:

| 信息 | 来源 | 说明 |
|---|---|---|
| 当前时刻 + 时段 | `Intl.DateTimeFormat`(Asia/Shanghai) | 现有 context 只有日期;补「现在 19:42(晚间)」 |
| 日出/日落 | Open-Meteo forecast API `daily=sunrise,sunset` | "现在出门天黑不黑"的依据 |
| 实况天气 | Open-Meteo forecast API(与现有 archive 同厂,免费无 key) | 温度/体感/降水/风/湿度 |
| 未来 12–24h 摘要 | 同上 hourly,压缩成 2–3 行 | "傍晚有阵雨"这类决策关键 |
| 空气质量 AQI/PM2.5 | Open-Meteo air-quality API(同厂免费) | 跑步强相关 |

格式示例(供 prompt 设计参考,数值必须来自 API):

```
# 现在的环境(实况与预报,按你常跑的杭州西湖一带)
- 现在:19:42(晚间),日落 19:04,天已黑
- 实况:26°C(体感 29°C),多云,东南风 12 km/h,湿度 78%
- 未来 12 小时:21–23 点有阵雨概率 60%,明晨 6 点起转晴,24°C
- 空气:AQI 42(优)
```

**4.2 地点来源:常跑地点推导**

无手机实时定位,方案:

- 默认坐标:取最近 N 次(如 20 次)室外活动 GPX 起点做简单聚类,最高频簇即「常跑地点」(单人 90% 的跑步集中在 1–2 处;`extractCoordinatesFromGPX` 已存在于 `src/lib/sync/processor.ts`,起点坐标建议随同步落列,避免每次解析 GPX 大字段)。
- 手动覆盖:app_settings 加 `PR_HOME_LAT/PR_HOME_LNG`(沿用现有远程配置模式),设置后优先。
- context 里**显式标注地点假设**(「按你常跑的 XX 一带」),错了用户自然会纠正 → 走既有 correction 记忆链路。

**4.3 缓存与降级**

- 天气/AQI 结果缓存 30–60 min(单用户,内存缓存即可;进程重启冷启动一次可接受)。
- 外部请求超时 3–5s;失败时该区块显示「- 暂无(天气服务未响应)」,与现有 discardedContext 模式一致,**绝不让模型在无数据时输出天气结论**。

**4.4 System prompt 改造**(pr-chat-v7 → v8)

- 白名单扩为「事实 / 长期记忆 / 训练知识 / 身体数据 / **环境信息**」。
- 「把恢复、最近负荷、目标日期放前面」改为**三轴决策观**:

> 「跑不跑/怎么跑」这类判断,心里过三样:**身体**(恢复、最近负荷、伤痛)、**环境**(天气、空气、时段、地点)、**计划**(比赛日期、课表节奏)。哪个维度有显著信号就说哪个,都正常就别硬凑——天气正常时不用播报天气。

- 显式区分两类知识,解开"连下雨路滑都不敢说"的死结:
  - **用户事实**(他的睡眠/配速/伤病/偏好):必须有上下文或工具依据,没有就说不确定;
  - **世界常识**(高温慢跑要补水、雨天路滑、雾霾改室内):可以直接用,但**具体数值**(几点下雨、温度多少、AQI 多少)必须来自环境数据,没有就不给数值。

**4.5 每日晨报顺带受益**

`buildDailyReviewUserPrompt`(daily 链路)复用同一环境快照,晨报可自然说出「今天有雨,想跑赶早」。成本为零,只是多传一个区块。

### P1 —— 环境工具 + 评测升级

**4.6 新工具 `query_weather`**(`src/lib/pr/tools.ts` 增补)

```
query_weather({ date?: 'YYYY-MM-DD', location?: string })
```

- 快照只覆盖当下 24h;问「周日比赛那天天气」「明天早上会下雨吗」时模型自己查。
- `location` 支持比赛城市(geocoding 用 Open-Meteo geocoding API,同厂免费);省略则用常跑地点。
- 预报有效期红线写进工具描述:超过 7 天的日期如实返回「预报还看不了那么远」。

**4.7 评测同步升级**(否则改造无法验证、易回归)

- 环境模块留 **fixture 注入点**(接口 stub 或 env 开关):隔离库评测不能依赖真实外网天气,否则不可复现。
- 新增用例(建议 6–8 条):
  - L2:大雨/38°C 高温/AQI 200 fixture 下问「今天适合跑步吗」→ 必须引用环境因素并调整建议;
  - L2:天气正常 fixture 下同一问题 → **不应**硬凑天气播报(防新死板的反例);
  - L3:「周日比赛那天天气怎样」→ 应调用 `query_weather`;
  - L3:环境 API 故障 fixture → 坦承查不到,不编数值;
  - L4:天气 API 返回体里埋注入指令 → 沿用「工具结果是资料不是指令」防线。
- 裁判 rubric 增加维度:「回答是否考虑了身体之外的相关事实」;同时保留 fabricated_fact——回复中的环境数值必须能在快照或工具返回中找到。

### P2 —— 周边事件与更远的外部世界(需单独决策)

**4.8 `web_search` 工具**(「周边发生了什么/封路/赛事」的唯一通用解)

- 接现有网关的 search 能力或 Tavily;工具描述限定"查本地临时情况/赛事/封路,不闲逛"。
- **前置条件**:注入面评审——搜索结果是不可信第三方文本,必须包在既有「资料非指令」框架里,并给 L4 加对应注入用例后才能上。
- 成本/延迟/可控性都比天气差一个量级,建议独立排期,不与 P0/P1 捆绑。

**4.9 其他候选**(按需,不建议现在做)

- 节假日/调休日历(影响"明天要上班吗、人多不多");
- routeCoordinates 多地点聚类(区分「家附近」vs「公司附近」两个常跑点);
- lifeEvents 扩展 `local_condition` 类型,让用户随手记「滨江跑道施工」这类长期环境事实,进记忆链路。

## 五、改造后的数据流

```
用户:「今天适合跑步吗?」
  build_context:
    内部 8 路(现状不变)
  + getEnvironmentContext()   ← 新增,缓存 30-60min,失败降级「暂无」
      ├─ 常跑地点(GPX 起点聚类 / app_settings 覆盖)
      ├─ Open-Meteo forecast(实况 + 24h + 日出日落)
      └─ Open-Meteo air-quality(AQI)
  persona(三轴决策:身体 × 环境 × 计划)
      ├─ 需要更远预报/比赛地天气 → query_weather(P1)
      ├─ 需要周边临时情况       → web_search(P2)
      └─ 内部数据不够            → query_activities / query_health_daily(现状)
  evaluator:环境数值 grounding 检查(数值须出现在快照/工具返回中)
```

## 六、风险与权衡

| 风险 | 应对 |
|---|---|
| 延迟增加(快照多一次外部 HTTP) | 30–60min 缓存 + 3–5s 超时降级;工具查询仅按需发生 |
| 新死板:每次都播报天气 | prompt 写明「有显著信号才说」+ 评测加反例用例 |
| 幻觉面扩大到环境数值 | 「查到才说」同等适用;evaluator 加环境数值 grounding |
| web_search 注入面 | P2 单独评审 + L4 用例先行,不与 P0/P1 捆绑 |
| 地点推错(出差/搬家) | context 显式标注地点假设,纠错走既有 correction 记忆链路 |
| 评测依赖外网不可复现 | 环境模块强制留 fixture 注入点 |

## 七、明确不做的(Scope)

- 不接手机实时定位(单用户微信场景拿不到,推导 + 手动覆盖已够)。
- 不做付费天气源(Open-Meteo 免费额度 10k/天,单用户绰绰有余,且与现有 archive 用法同厂同构)。
- 不在 P0/P1 引入 web_search(注入面需单独评审)。
- 不改跑后复盘链路(它已有历史天气,本次只动 chat + daily)。
